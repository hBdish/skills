# Как добавить или изменить скилл

Для тех, кто пишет скиллы. Как ими пользоваться — в [README.md](README.md).

## Структура репозитория

```
skills/<группа>/<имя>/        единственный источник правды
  SKILL.md                    frontmatter (name, description) + процедура
  references/                 детали, агент читает по требованию
  scripts/                    детерминированные проверки (Python, только stdlib)
  evals/                      trigger-evals.json + evals.json (+ files/ с фикстурами)
profiles.json                 наборы скиллов для установки
templates/skill/              шаблон нового скилла
scripts/
  install.py                  установка в проекты
  validate.py                 проверка по спецификации и правилам репозитория
  new_skill.py                создать скилл из шаблона
AGENTS.md                     инструкции для агента, работающего над этим репозиторием
```

Группы нужны людям: `lang` (язык), `framework` (фреймворк поверх языка), `practice` (процесс: ревью, коммиты, тесты), `tooling` (инфраструктура), `meta` (работа со скиллами). Агент видит все скиллы в одном плоском списке, поэтому имя уникально по всему репозиторию.

## Как устроен скилл

Скилл загружается в три этапа, и все правила ниже следуют из этого:

| Этап | Что загружается | Когда | Бюджет |
|---|---|---|---|
| 1 | `name` + `description` | всегда, для каждого установленного скилла | ~100 токенов |
| 2 | тело `SKILL.md` | когда агент выбрал скилл | до 500 строк |
| 3 | `references/`, `scripts/`, `assets/` | когда шаг инструкции их требует | без ограничений |

## Новый скилл по шагам

**0. Убедитесь, что нужен новый скилл.** Сначала напишите `description`. Если реальный запрос подходит и под него, и под существующий скилл, расширьте существующий (новый файл в `references/`). Разные языки — разные скиллы; стиль языка и его тесты — один скилл.

**1. Соберите примеры.** 3+ реальных запроса, на которые скилл должен сработать, и ожидаемый результат. Правила, придуманные без примеров, получаются общими словами.

**2. Создайте каталог:**

```bash
python3 scripts/new_skill.py lang rust-style
```

**3. Напишите frontmatter.** Только поля из спецификации:

```yaml
---
name: rust-style                 # == имя каталога: a-z, 0-9, одинарные дефисы
description: <что делает>. Use when <контексты, типы файлов, слова пользователей>. Do NOT use for <похожие задачи, с именами соседних скиллов>.
license: MIT
metadata:
  version: "0.1.0"
---
```

`description` решает, сработает ли скилл вообще:
- 300–700 символов, главное — в первых 150 (часть агентов обрезает хвост);
- уверенно: «Use whenever Rust code is written or reviewed, even if style was not mentioned» работает лучше, чем «Can help with Rust»;
- в «Use when» — реальные формулировки и типы файлов (`.rs`), в том числе по-русски, если так пишут запросы;
- в «Do NOT use for» — похожие задачи с именем скилла, который за них отвечает. У соседа добавьте встречную фразу.

**4. Напишите тело** — процедуру, а не справочник. Английский, повелительное наклонение.

| Материал | Куда |
|---|---|
| Порядок шагов, как принимать решение, формат ответа | `SKILL.md` |
| Точные правила, таблицы, краевые случаи, длинные примеры | `references/<тема>.md` + в `SKILL.md` фраза «читай X, когда Y» |
| То, что можно вычислить: линтер, парсинг, проверка | `scripts/<name>.py` |
| Файлы, которые попадают в результат: шаблоны, схемы | `assets/` |

Правила хорошего тела:
- **Правила проекта главнее скилла.** Сначала конфиги и существующий код, потом умолчания скилла.
- **Объясняйте «почему».** Модель, которая знает причину, правильно справится со случаем, которого нет в инструкции. MUST/NEVER — только там, где нарушение ломает результат.
- **Один хороший пример лучше трёх абзацев.** Покажите вход → выход для нужного формата.
- **Скажите, что делать без инструмента.** Скрипт, который не запустился, не должен выглядеть как «всё чисто»: печатайте `SKIP`.
- **Правило живёт в одном скилле.** `practice` не повторяет языковые правила, `lang` не описывает процесс.

**5. Сделайте скилл переносимым:**
- скрипты на Python 3.8+, только stdlib, `pathlib`, `encoding="utf-8"`; никаких bash и PowerShell;
- внешние инструменты — через `shutil.which`, их отсутствие — `SKIP`;
- ссылки относительные и только внутри каталога скилла (при установке копируется только он);
- без названий инструментов конкретного агента: «найди в коде», а не «используй Grep».

**6. Напишите евалы.** Две независимые оценки:

`evals/trigger-evals.json` — срабатывает ли скилл, когда нужно:

```json
[
  {"query": "глянь перед PR: fn parse(s: &String) -> Option<i32>", "should_trigger": true, "note": "ревью, основной случай"},
  {"query": "почему cargo build тянет две версии tokio", "should_trigger": false, "note": "near-miss: Rust, но зависимости"}
]
```

- ~20 запросов, примерно поровну положительных и отрицательных;
- отрицательные — только near-miss: та же лексика, другая задача. Очевидно нерелевантные ничего не измеряют;
- прогонять каждый запрос 3+ раз: срабатывание случайно.

`evals/evals.json` — лучше ли результат со скиллом, чем без него: тот же запрос, та же модель, со скиллом и без. Ожидание, которое выполняется и без скилла, ничего не проверяет — перепишите его. Обязателен кейс с чистым входом: скилл не должен выдумывать проблемы. В Claude Code евалы удобно гонять скиллом `skill-creator`; в других агентах — неинтерактивным режимом (`codex exec`, `gemini -p`, `claude -p`).

**7. Добавьте скилл в профиль** в `profiles.json` (не больше 8 скиллов в профиле).

**8. Проверьте:**

```bash
python3 scripts/validate.py --strict
```

```bash
python3 scripts/install.py --skill rust-style --project /path/to/test-project
```

Перезапустите агента в тестовом проекте и попробуйте запросы из `trigger-evals.json`.

## Изменение существующего скилла

- Тело — обычный PR.
- `description` — breaking change: меняется, когда скилл срабатывает, и он может начать перехватывать запросы соседей. Перепрогоните `trigger-evals.json` свой и соседей, названных в «Do NOT use for».
- Поднимите `metadata.version`.
- Контент, выведенный из внешнего источника (как `go-style` из Google Go Style Guide): указывайте URL и дату синка в шапке файла и пере-выводите из источника, а не латайте на месте.
- Удаление скилла — удаление каталога и записи в `profiles.json`. Заглушки «deprecated» не оставлять: они продолжают перехватывать запросы.

## Чек-лист ревью

- [ ] `validate.py --strict` проходит (CI это проверяет на Ubuntu, macOS и Windows).
- [ ] Содержимое не выходит за то, что обещает `description`.
- [ ] Границы с соседями прописаны с обеих сторон.
- [ ] Есть оба набора евалов, включая кейс с чистым входом.
- [ ] Скрипты не тянут зависимостей и не ходят в сеть молча.
- [ ] Нет секретов, внутренних URL и данных: скиллы копируются в чужие проекты и попадают в контекст модели.
